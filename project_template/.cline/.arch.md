# Cline

Cline is an AI pair programming tool that can edit code and manage repositories through natural
language prompts.

## Why this template uses Cline

Cline provides interactive and one-shot CLI sessions in the development container, along with
commands for creating, resuming, and managing isolated worktrees. This lets developers use the same
containerized project tasks for both direct work and parallel agent sessions.

## Usage

Start an interactive session in the development container with `./task.sh cline:launch`. Alternatively,
run a one-shot command with `./task.sh cline:launch "instructions for cline"`. Use `cline:worktree`
to create a worktree and `cline:worktree-resume` to resume one. `cline:worktree-shell`,
`cline:worktree-save`, and `cline:worktree-cleanup` support managing worktrees. All Cline tasks
share the same key and proxy configuration.

## Shared provider proxy

The proxy is optional. To use it, copy `.cline/.env.example` to `.cline/.env` and set a real
`UPSTREAM_API_KEY`. You can also set `UPSTREAM_URL`, `UPSTREAM_AUTH_HEADER`, and
`UPSTREAM_AUTH_SCHEME`. Do not commit `.cline/.env`.

Running `./task.sh cline:launch` starts the shared proxy on demand and attaches the development
container to `agent-mesh`. The real provider key is passed only to the proxy. Configure Cline's
OpenAI-compatible provider with base URL `http://ai-proxy:4000` and a dummy API key. The proxy is
reachable at `ai-proxy:4000` only from containers attached to `agent-mesh`.

The proxy is a singleton with one upstream configuration shared by all projects. The first project
that starts it supplies the provider account and key. All projects using the proxy must use that same
account and key. Changing the configuration requires recreating the `ai-proxy` container. Without
`.cline/.env`, Cline tasks leave provider settings untouched and launch Cline normally, so you can
use Cline's own provider setup. Non-Cline tasks do not need proxy credentials or a Cline environment
file.

Each Cline worktree gets an isolated `.cline` config and data directory. Provider and model settings
are stored in `.cline/data/settings/providers.json`; session history is stored under `.cline/data`.
Existing worktree provider settings are preserved. Otherwise, they are initialized from the project
settings.

The proxy forwards request paths beneath `UPSTREAM_URL`; use the provider origin, such as
`https://api.openai.com`. Optional `MODEL_MAP` JSON translates model names, and `ROUTE_MAP` JSON maps
incoming path prefixes to upstream path prefixes. Upstream rate-limit telemetry is available at
`GET /rate-limits`. A 429 `Retry-After` header causes a bounded cooldown shared by requests handled
by this proxy process, not across proxy replicas.

The practical reason for using the proxy is to keep parallel Cline sessions from independently
flooding the provider and hitting rate limits. Without shared coordination, a provider `429` error
can interrupt a request and cause Cline to stop that work. Sessions using this proxy share one
request/token capacity queue: the proxy waits for configured capacity before forwarding requests,
and retries transient `429` responses with bounded delays. This reduces rate-limit errors and
session interruptions; it cannot prevent every error, since provider limits can differ from the
proxy's settings and retries are bounded.

The proxy also shares one upstream provider credential with Cline projects and provides the few
model/path mappings and rate-limit controls used by this workflow. It is deliberately implemented
as a small Python standard-library service rather than adopting a general-purpose LLM gateway.
Fewer components and features mean less code in the credential-handling path to inspect and audit,
and less functionality to maintain that this workflow does not need.

The motivation is risk reduction, not a claim that custom software is inherently safer. Proxies that
become popular can be high-value targets because they handle provider credentials. For example, on
October 21, 2026, LiteLLM reported that its release pipeline was compromised and published a
credential-stealing `v1.107.0` release to PyPI and container registries. This was a compromise of
release artifacts, not evidence that every deployed LiteLLM proxy was directly exploited. See the
[LiteLLM incident report](https://docs.litellm.ai/blog/security-incident-oct-21-2026) and
[Microsoft's analysis](https://www.microsoft.com/en-us/security/blog/2026/10/23/inside-the-litellm-1-107-0-supply-chain-compromise-credential-theft-through-python-startup-hooks/).

This small proxy also has real costs: it is project-owned software that must be reviewed, tested,
and updated, and it still has access to the upstream key. Use a general-purpose gateway when its
broader provider support, integrations, or operational features are needed; this service is not a
drop-in replacement for those capabilities. The proxy is optional—users can instead configure
Cline's provider directly. When enabled, protect the proxy image and configuration, and do not
commit `.cline/.env`.

Use `/` to see the built-in commands and documentation.
