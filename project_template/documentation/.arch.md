# [Documentation](../.arch.md#documentation)

This directory contains the project's [StrictDoc](https://strictdoc.readthedocs.io/) sources.

Use this file for documentation authoring and tooling. The
[development process](docs/00-process/00-development-process.sdoc) defines project lifecycle,
tailoring, and release criteria. General authoring and design decomposition rules are in
[`.cline/rules/documentation.md`](../.cline/rules/documentation.md).

## Repository layout

- `00-process`: lifecycle and project management
- `01-requirements`: needs, behavior, constraints, and acceptance criteria
- `02-design`: architecture, components, interfaces, and decisions
- `03-implementation`: tasks, tests, executions, and evidence
- `04-milestones`: readiness gates and decisions
- `05-safety-assurance`: hazards, controls, safety functions, and claims
- `06-security-assurance`: assets, threats, controls, vulnerabilities, incidents, and claims

Directories organize files; stable UIDs and StrictDoc relations provide identity and traceability.

## Build, serve, and format

Build the static site and PDFs:

```shell
./task.sh documentation:build
```

Serve the site with live editing at <http://0.0.0.0:5111>:

```shell
./task.sh documentation:serve
```

Rewrap `.sdoc`, `.md`, and `.template` files in `/docs` to 100 columns:

```shell
./task.sh documentation:format
```

## StrictDoc conventions

Each traceable document defines its grammar. Inspect it before changing fields or records. Follow
[the documentation rules](../.cline/rules/documentation.md) for stable UIDs, relations, traceability,
and source links. Use `[TEXT]` nodes for explanatory Markdown; keep normative behavior in traceable
records. A successful export checks neither technical correctness nor approval.

After changing a grammar, UID, field, choice, relation, or document path, run a full build and review
all reported errors.

The statistics generator (`docs/sdoc_project_statistics.py`) reads the custom `REQUIREMENT`,
`DESIGN`, `IMPLEMENTATION`, `MILESTONE`, `SAFETY`, and `SECURITY` node types. When a grammar or
workflow value changes, check whether the generator needs an update, then build and review counts,
drill-down links, and the separation of `template` records. Statistics are review aids, not approval
or release evidence.

## Diagrams

Markdown fields support Mermaid for workflows and dependencies, and PlantUML for architecture,
sequence, component, and state views. Keep diagram names consistent with traceable records; show
relevant boundaries; do not introduce behavior absent from normative records; and update diagrams
when associated records change. Diagrams support understanding but do not replace records or evidence.

## External work-management integration

Git-managed StrictDoc sources are authoritative unless a project explicitly defines otherwise. An
adapter may synchronize planning or assignment data, but must map stable UIDs to explicit remote
identifiers, never infer identity from titles or descriptions, and validate local changes.

Adapters must provide deterministic mapping, ambiguity and duplicate detection, field ownership,
reviewable changes, conflict reporting, no-op behavior for equal values, provenance, and baseline
handling. They must not store credentials in project files or silently mutate an authoritative
branch. Keep provider-specific mappings and conflict policies in adapter configuration. Remote
status and approvals do not replace controlled verification or project approval.

## Cross-repository components

Manage external components as pinned vendored dependencies, not Git submodules. Declare each
repository and version in the root `strictdoc.deps.yaml`, then fetch pinned versions with:

```shell
python fetch_deps.py
```

Include vendored documentation paths in `strictdoc_config.py` `input_paths` so StrictDoc indexes
cross-repository UIDs and relations. The component repository owns its internal records; the product
repository owns product requirements and allocates them to component requirements through design
relations. Do not copy shared records into product sources or edit generated copies. Product records
must identify the component baseline, allocation, integration work, and product verification.

## Evidence and review

Use durable, access-controlled evidence; do not rely only on dashboards, transient URLs, unversioned
files, remote workflow states, or generated pages. Preserve failed and blocked execution history by
adding a new execution record for each rerun. Retain closed vulnerability and incident records as
product history.

Before submitting, verify that the authoritative source was edited; UIDs, fields, and relations are
valid; placeholders are intentional; diagrams agree with normative records; cross-repository links
identify immutable baselines; the build succeeds; traceability and statistics were reviewed; and no
generated output, credentials, or transient evidence was committed.

## Editor support

VS Code is preferred. Optional extensions: [Markdown Preview Enhanced](https://marketplace.visualstudio.com/items?itemName=shd101wyy.markdown-preview-enhanced) and
[markdownlint](https://marketplace.visualstudio.com/items?itemName=DavidAnson.vscode-markdownlint).

The `documentation:markup-to-markdown` task is not yet implemented. Review converted content
manually: conversion does not create valid requirements, UIDs, relations, approvals, or verification
evidence.
