# Cline

Cline is an AI pair programming tool that can edit code and manage repositories through natural
language prompts.

## Usage

Start an interactive session in the development container with `./task.sh cline:launch`. Alternatively,
run a one-shot command with `./task.sh cline:launch "instructions for cline"`. Use `cline:worktree`
to create a worktree and `cline:worktree-resume` to resume one. `cline:worktree-shell`,
`cline:worktree-save`, and `cline:worktree-cleanup` support managing worktrees. All Cline tasks
share the same key and proxy configuration.

Use `/` to see Cline's built-in commands and documentation.

Also see [the official published Cline documentation](https://cline.bot/cli).

## Optional shared AI proxy

The proxy runs as a separate Compose service so it can remain available while short-lived
development containers start and stop. Proxy configuration is optional and stored under
`.cline/`, separate from general project environment settings:

```bash
cp .cline/.env.example .cline/.env
# Edit .cline/.env and set UPSTREAM_API_KEY and any provider-specific settings.
./task.sh cline
```

When `.cline/.env` contains an upstream key, Cline tasks start the proxy on demand. Configure
Cline's OpenAI-compatible provider manually with base URL `http://ai-proxy:4000` and a dummy API
key to route requests through it. Without proxy configuration, existing Cline provider settings
are left alone so Cline can be used directly. Other Compose services and non-Cline build tasks
do not require proxy credentials. The first opted-in Cline task starts the proxy and attaches the
already-running developer container to the shared `agent-mesh` network. The proxy is reachable as
`ai-proxy:4000` only from attached developer containers and is not published on a host port.
The singleton uses one upstream provider configuration and API key shared by all projects; the first
project that starts it supplies those settings.

The proxy forwards requested paths and query strings under `UPSTREAM_URL` (set it to the provider
origin, such as `https://api.openai.com`), and can map model aliases with `MODEL_MAP` and path
prefixes with `ROUTE_MAP` JSON objects in `.cline/.env`. Upstream rate-limit headers are exposed
at `GET /rate-limits`; responses
also preserve relevant rate-limit headers. A 429 response with `Retry-After` pauses subsequent
requests through this proxy process for the bounded cooldown. This in-memory limit state is shared
by clients of one proxy instance, but not across proxy replicas.

## Docker-out-of-Docker worktree paths

Tasks are run from a top-level container. Some of those tasks launch a secondary container in a
Docker-out-of-Docker context via the host Docker socket. In this case, the host workspace volumes
must be mounted to the secondary container, not the workspace volume from the top-level container.

The secondary containers might be launched from a root git worktree, or from a linked worktree
under the folder `.cline/worktrees/`.

In all cases, the top-level container will be launched from the root git worktree. Tasks that
launch a secondary container must check what worktree they're originating from, and modify the
host working directory that gets mounted to the secondary containers.

`task.sh` will pass in the environment variable `HOST_PWD`, which will be the path of the root
worktree on the host.

The following built-in Go Task variables can be used to get the locations of Taskfiles:

- `{{.TASKFILE_DIR}}`: Path of the Taskfile where the task being run is defined
- `{{.ROOT_DIR}}`: Path to the directory of root Taskfile.yaml of the worktree

Docker compose files can mount a volume using a variable path that adjusts for the worktree, such
as `DOCKER_MOUNT_PATH`.

Here is an example of tasks that are setup to work in these contexts:

```yaml
var:
  _docker-run:
    internal: true
    dir: '{{.TASKFILE_DIR}}'
    vars:
      DOCKER_MOUNT_PATH: '{{.HOST_PWD}}/{{ trimPrefix "/workspace/" .TASKFILE_DIR }}'
    cmds:
    - DOCKER_MOUNT_PATH="{{.DOCKER_MOUNT_PATH}}" docker compose run --rm --service-port example-container {{.CMD}}

  example-1:
    cmds:
      - task: _docker-run
        vars: { CMD: "short_example_command"}

  example-2:
    cmds:
      - task: _docker-run
        vars:
          CMD: >
            command --that --spans
            --multiple --lines
